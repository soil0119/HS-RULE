# 검색·답변 튜닝 절차 (#77·#78)

실제 임베딩·실제 모델을 연결한 뒤(#76) 이 절차로 기준선을 만들고 설정을 비교한다. 대역(standin) 결과는 파이프라인 점검일 뿐이며 튜닝 판정에 쓰지 않는다. 지금 평가 말뭉치는 학칙 발췌본 하나(청크 약 20개)라 Recall@5가 쉽게 높게 나온다. 실제 스냅샷(#60·#68)으로 바꾼 뒤의 기준선을 판정 기준으로 삼는다.

## 실행 순서

1. 기준선: 현재 기본값(근거 k=6, 검색별 후보 20, 조항/키워드/벡터 가중치 3/1/1, 벡터 단독 cosine 0.25, 청크 128토큰·겹침 16)으로 `--split tune`과 `--split holdout`을 각각 실행해 결과 파일을 보관한다.
2. 한 번에 한 묶음만 바꾼다. 검색(#77: k·후보 수·가중치·threshold·청크 길이·임베딩)과 답변 흐름(#78: 프롬프트·재작성·조건 되묻기)을 동시에 바꾸지 않는다. 다른 쪽 설정은 고정한다.
3. 조정은 `tune` 결과만 보고 한다. 후보 설정이 정해지면 `holdout`을 한 번 실행해 판정한다. `holdout`을 보고 다시 조정했다면 그 결과는 최종 판정으로 쓰지 않고 새 확인 사례를 추가한다.
4. 임베딩 모델이나 청킹을 바꾸면 별도 일회용 DB에서 다시 색인한다. 서로 다른 모델의 벡터를 한 색인에 섞지 않는다(색인 메타가 거부한다).
5. 개선이 없었던 실험도 아래 표에 남긴다.

## 통과 기준 (제안: 튜닝 시작 전에 팀이 확정)

- `holdout` 검색 Recall@5가 기준선보다 낮아지지 않고, MRR 또는 Recall@1이 오른다.
- 근거 없음 사례의 무근거 답변률이 오르지 않고, 삭제 조항·권한·개정 회귀(`regressions`)가 모두 통과한다.
- 답변 인용 일치율과 수치 근거 통과율(`grounding.verified_rate`)이 낮아지지 않는다.
- 조건 되묻기: `asked_when_needed`가 오르면서 `unnecessary_rate`가 오르지 않는다.
- 검색 지연 p95와 답변 지연 p95, 질문당 모델 호출 수가 합의한 상한을 넘지 않는다.

## 알려진 실패 (대역 기준, 2026-11-27)

- `addendum-effective-2016`: "졸업학점 130학점 규정은 언제부터 시행됐나요?"에서 부칙(2016.2.3 공포) 제1조(시행일)가 검색 5위 안에 없다. 본칙 조항과 그 조항을 바꾼 부칙의 시행일이 연결되지 않는 문제다. 실제 임베딩 기준선에서 다시 확인하고, 필요하면 개정 부칙 연결(질의 확장·참조 확장)을 실험한다.

## 되돌리기

설정은 코드 상수(`hsrule/official_retrieval.py`, `hsrule/chains.py`)와 환경변수(`RAG_RETRIEVAL_K`)로 정한다. 이전 값으로 되돌리면 되고, 임베딩·청킹을 바꾼 경우에만 이전 설정으로 다시 색인해야 한다. 관리자 화면에 노출할 항목(#75)은 기준선 결과로 확정한 뒤 범위·적용 시점·재색인 필요 여부와 함께 인계한다.
